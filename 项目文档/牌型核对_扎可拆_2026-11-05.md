# 牌型核对：扎牌可拆（"上/可/三 扎·穿切换"牌型）2026-11-05

## 原型（用户给）

`上上上上 可可可可 乙二三 四五六 八九子 七十土 化三千 三叁叁赖赖`（28 张，扎了三次）

用户给出的四种胡牌拆法（覆盖全部 22 字）：

| 统牌 | 拆法 | 用户计胡 |
|---|---|---|
| 上 / 大 / 人 | 上上上（坎）＋上（摞）＋可可可可（扎）＋5 顺＋三叁叁赖赖（穿） | 107 |
| 可 / 知 / 礼 | 上上上上（扎）＋可可可（坎）＋可（摞）＋5 顺＋三叁叁赖赖（穿） | 107 |
| 化 / 千 | 上扎＋可扎＋5 顺＋叁叁赖赖（扎）＋三（摞） | 62 |
| 乙/二/三/四/五/六/七/八/九/子/十/土/孔/己 | 上扎＋可扎＋乙二三四五六七（乙或四或七摞）＋八九子＋赖十土＋化三千＋三叁叁赖（扎） | 52 |

要点：**扎牌可以退回成"坎(3 张) + 1 张自由牌"**，那 1 张再与统牌凑成摞（眼）；也可以收缩成"2 张 + 2 赖"的扎，把腾出的字让给听口。所以三个扎不是三把锁，而是三处可调的结构。

## 引擎实测

### 1. 结构：完全能表达 ✅

按拆法 A 精确构造（扎(可) 4 张 + 穿(三三三赖赖) 5 张 + 手牌 + 统牌上）：

```
zha(可可可可)  chuan(三三三赖赖)  pair(上上)  seq(乙二三)  seq(四五六)
seq(八九子)    seq(七十土)        seq(化三千)  pen(上上上)
```

判胡成功。拆法 B（扎上 + 坎可 + 摞可）同样成立。
**说明引擎的拆分器能处理这种重组，缺的不是能力。**

### 2. 流程：不会自动尝试 ❌（这是 16/22 的真正原因）

若按当前锁定状态判定（扎上 + 扎可 + 扎三，直接判胡上），结果为 `null`（不胡）。
页面只在 `checkResponseAfterOpponent`（L7070-7095）对**含赖子的扎牌**做一次"释放重分配"重试：

```js
if (zm.type === 'zha' && zm.cards.some(c => c.isWild)) { ...释放此扎牌... }
```

纯物理扎（上扎、可扎）一律不放行 → 实测该牌型只能胡 16 字，缺 `上大人可知礼` 6 字（正好是要靠拆扎才能胡的两个顺子成员）。

### 4. 剩下的两处真实差异

**差异①：精牌摞（眼）的计胡**
`_makeCardData('三','skin')` 两张 → 引擎 4 胡，用户 2 胡。疑点：主精翻倍是否应作用于"摞/眼"这张牌型。

**差异②：引擎不允许"统牌充当摞"**
拆法 A 里用户的分解是「坎(上上上) + 摞(统牌上 + 手牌上)」，合计 2 胡；
引擎给出的却是「碰(上上上，统牌在其中) + 对子(上上)」，合计 0 胡。
按"拆分以胡数最大为原则"，引擎本该翻出 2 胡的那种——说明它没把"统牌做摞"作为候选。

### 5. 与用户 108/64 的差额来源

- 拆法 A：用户 108 = 坎2 + 扎4 + 5 顺(6) + 穿96 + 摞0
  引擎 106 = 碰0 + 扎4 + 6 + 96 + 对子0（差的就是"坎 2 胡 / 统牌摞"这 2 胡）
- 拆法 C（胡化千）：用户 64 = 扎4 + 扎4 + 顺(6) + 扎(叁叁赖赖)48 + 摞(三)2
  → 需要引擎允许"扎从 3 张收缩到 2 张+2 赖"，并把腾出的三用作摞

## 建议改动（待你点头）

1. **扎牌可拆**（核心）：判定时对每个 inHand 扎枚举 扎(4张) / 坎(3张)+1自由牌 / 穿(5张) 取最优
